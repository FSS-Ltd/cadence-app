# Cadence Implementation Plan

> **Delivery rules:** Each numbered build row below is a standalone step. Implement and verify it, open its PR, wait for current-revision CI to pass, verify merge to the designated base, and record that evidence before starting the next row. Production deployment remains separately authorised. Historical research remains reference evidence; current requirements and numbered gates govern implementation.

**Goal:** Build a dependable five-network social media planning, review, scheduling and posting web app for Jean and his wife, with multiple accounts, Teams permissions and commercial plan enforcement from the first build; prepare the AI pipeline now, then activate funded AI/native offline AI and expand publicly.

**Architecture:** A modular Next.js application on Vercel, with Clerk identity and Supabase Postgres/private Storage. Workspace entitlements and live membership permissions protect multiple social accounts; durable jobs execute approved publications independently of phones and AI. Build model-independent AI task/queue/proposal boundaries initially; connect hosted and offline native model runtimes only when funded. Privacy acceptance applies at every build step; see the [privacy architecture](../Cadence-Privacy-Architecture.md).

**Tech Stack:** Strict TypeScript, Next.js App Router, React, Node.js LTS, Supabase, PostgreSQL SQL migrations/generated types, pnpm, Zod, Vitest and Playwright; SwiftUI and a tested local-model runtime in the later native phase.

## Review Focus

1. Provider accepted a post but its response was lost: retain an uncertain outcome and reconcile before any fresh create request. Owned by Phase 2 failure tests.
2. An editor changes public content after approval: reject scheduling of the new revision under the old approval; retain immutable history. Owned by Phases 1–2 approval tests.
3. Two workers or users race on the same publication: one valid transition/claim; stale lease completion cannot overwrite newer state. Owned by Phase 2 transaction tests.
4. A local time is missing or repeated at a daylight-saving change: require an explicit valid time/offset and preserve Europe/London context. Owned by Phases 1–2 calendar tests.
5. Indirect IDs, stale roles or two simultaneous last-slot connections bypass isolation/plan limits: deny unauthorised actions and atomically enforce account/seat limits. Owned by Phases 1 and 5 isolation/entitlement tests.

## 3. System architecture and trust boundaries

```text
USER DEVICE: browser / Home Screen web app
  private content in memory; authorised transfers; no persistent content cache
             |
             v
VERCEL lhr1: authenticated Next.js API + domain services
  Clerk-verified identity + fresh-session policy + live DB grants/plan -> commands
             |
             v
SUPABASE eu-west-2: Postgres + private Storage, user-scoped RLS
  workspace/brand data | immutable revisions | approval/publication state
  private credentials | durable jobs | safe attempts/audit | plans/memberships
  prepared AI task/run/proposal state (production generation disabled)
             ^
             |
VERCEL CRON -> bounded publisher -> official authorised social APIs
               claims/checkpoints     returned IDs + status reconciliation

FUTURE FUNDED BOUNDARY
  hosted AI / native offline AI -> editable proposal -> existing revision service
  publishing, approval, credentials and calculations remain application-owned

CLERK (US identity processing): verified subject/session and required MFA claims;
  no content, client notes, captures, social tokens or user-generated metadata

ISOLATED LONDON BACKUP TASK -> encrypted DB + media + key-dependency manifests
  -> dedicated encrypted S3 bucket; restore gated by independent deletion replay
```

Verify Clerk tokens through its supported Supabase third-party integration and authorise each workspace/brand/action using live database membership, grants and current entitlement. Internal UUIDs map to unique Clerk subject strings. User-scoped access uses RLS; restricted server operations use narrowly granted roles and transaction-local actor context. Plan eligibility, feature availability, role permission and provider permission are separate gates. Social sign-in to Cadence is separate from granting publication access to a specific social account. Missing/unknown closed-pilot policy denies access. See the [privacy architecture](../Cadence-Privacy-Architecture.md).

Upload media directly to a private bucket through authorised scoped URLs; persist immutable keys/checksums and readiness before approval. Do not proxy large assets through ordinary web-function request bodies. External provider processing becomes checkpointed jobs, not an open browser session.

## 5. Security and technical compliance

- **Identity:** Clerk email/password with verified email; closed registration and exactly two designated FSS pilot identities. Build/test TOTP MFA and backup-code recovery now; the exception is limited to the protected closed-pilot policy, while public access requires verified MFA claims across every API/Storage path. Require fresh authentication within ten minutes for sensitive actions.
- **Email:** configure an existing FSS SMTP service or an acceptable free SMTP plan for invitations/recovery. Prove delivery before the pilot. Supabase's default SMTP is restricted and unsuitable for dependable production email; do not solve this by adding users as database administrators. Public onboarding has a separate delivery/abuse gate. [SMTP requirements](https://supabase.com/docs/guides/auth/auth-smtp)
- **Permissions:** RLS plus minimal grants on exposed tables; DB membership/brand permissions rather than user-editable identity metadata. Workspace owner/admin status never reveals creator-private captures. Private tokens/jobs remain outside the browser-exposed schema. Test reads and every mutation, including indirect IDs, Storage and server-role paths. [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
- **Commercial/team gates:** protect plan/extra-seat assignments against self-upgrade; enforce network/account/seat limits transactionally and recheck before dispatch. Count owners and reserved unexpired invitations within five plus trusted grants. Seat reductions cannot erase content, orphan a last owner or silently remove members; reject internal reductions below occupied/reserved capacity until an explicit public reduction policy exists. Remove member access using live DB membership, not stale JWT roles. Owner/admin/editor/publisher permissions are separate from plan eligibility. Check session validity for sensitive commands; normal session tokens can outlive sign-out until expiry. [Session behaviour](https://supabase.com/docs/guides/auth/sessions)
- **Secrets:** encrypted social tokens; separate encryption key in platform secrets with key-version metadata. Redact logs; implement provider expiry/refresh/reconnect/revocation explicitly. Restrict token access to the publisher; native clients and future AI never receive it.
- **Web protection:** CSRF/origin protection for cookie-authenticated mutations, OAuth state and supported PKCE, allow-listed callback URLs, input/output escaping, bounded upload types/sizes and SSRF protection. Use public UUIDs as identifiers, not permission grants.
- **Prepared AI boundary:** treat imported text/media instructions as untrusted; enforce source/purpose/tenant permissions outside prompts. Validate task outputs and evidence IDs; the model gets no token, approval, account-change or publishing tools. Model-input rights are narrower than ordinary report-read rights. [Prompt-injection controls](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)
- **Audit/retention:** append-only approval/scheduling/cancellation/account-access events, with actor and correlation ID. Pilot defaults: operational logs 30 days; minimal audit records 180 days; backups 30 days; abandoned uploads/exports 24 hours; active-data erasure within 24 hours. Preserve user-owned drafts only until deletion; provider-derived data follows any stricter permitted-use/expiry rule. See [retention and recovery](../Cadence-Privacy-Architecture.md).
- **Privacy:** record source origin, owner, permitted uses and intended sharing. Drafts/source/media are private by default. Technical UK GDPR work includes processor inventory, deletion/export, documented purpose/retention and recovery procedures; London hosting is not a blanket compliance certificate. Recheck current ICO guidance before public launch. [ICO security guidance](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/security/a-guide-to-data-security/)
- **Verification:** threat review using relevant OWASP ASVS controls for auth/session/access control, validation, stored files and logging; check CSP, dependency updates and secret scanning in CI. [ASVS](https://owasp.org/www-project-application-security-verification-standard/)

## 6. Data model and storage

See [engineering contracts](../Cadence-Engineering-Contracts.md) for entities, relationships, indexes and illustrative SQL. Initial families: workspaces/members/roles, versioned plan assignments and usage reservations, brands/playbooks, authorised sources, immutable media, content items/revisions/source links, social accounts/capabilities, approvals, publications, jobs, attempts and audit. Prepare generation runs/proposals and task/prompt versions now; store real execution records only after funded activation.

Use tenant-scoped relationships to prevent a revision, account or source from another workspace being referenced accidentally. Store text and structured metadata in Postgres, original binaries in private Storage, and credentials in a private server-only structure. A revision's `contentHash` covers its canonical immutable public content/media. An approval's separate `approvalPayloadHash` binds the exact revision, destination account and canonical public payload; these hashes must not be compared as interchangeable values. Exclude temporary signed URL tokens and schedule time from content approval hashing.

Version brand guidance and source text when edits change evidence. Use Postgres full-text search initially. Prepare metric/video-evidence runtime schemas and immutable transcript/timeline identities in Phase 1; add metric snapshots, eligible retention series, transcript bindings/mappings and learning notes in Phase 3 when reporting needs them. All these are future application files. Generation run/proposal schemas and quota accounting are intentionally requested preparation; no model weights or embeddings are required initially. Keep analytics values, metric definitions, denominator/cohort, timing resolution, permission/expiry and sample windows attributable.

## 7. API design

Use `/api/v1` REST contracts with validated DTOs and explicit resource versions. The companion defines concrete approval/schedule examples, errors and adapter interfaces. Main commands create content/revisions, create a destination-specific publication, approve, schedule, reschedule/cancel and confirm manual publication. Separate account connection/callback/reconnect routes and a secret-authenticated internal sweeper.

Mutation safety: expected version plus idempotency key where appropriate, transactional membership/approval/media/capability checks, typed errors and audit. Return `409 VERSION_CONFLICT` for stale writes, `409 APPROVAL_REQUIRED` for an uncovered revision, and a recoverable reconnect/capability error rather than pretending success. A schedule acknowledgement means the durable server job exists; it does not mean a post is published.

Native sync later consumes these contracts. An offline change is unsynchronised local work until accepted by the server. Future generation returns draft proposals through the revision service and receives no approval/publication authority.

Add current-workspace entitlement/account/membership contracts and protected manual-destination, activation/invitation/acceptance/role/removal commands. Protect the last active owner under the workspace lock. Publication reads expose blocking reason/recovery actions; audited revalidation can resume eligible unsent work only after current approval/access/lateness checks. Initial AI request/proposal contracts return a truthful unavailable result while execution is disabled; test the authorised pipeline with isolated fixtures. Free requests must match its exact alt-text/analytics allow-list and finite quota; deny premium feature keys, task-family substitutions and disguised generation follow-ups. Entitled users still need a released feature and permitted inputs. Model credentials/outputs cannot bypass revision/evidence validation.

## 9. Backend and publishing plan

Keep Next.js route handlers thin. Focus modules on auth/membership, entitlements/usage, brands/sources, content/revisions, approvals/publications, storage, provider accounts, publisher jobs, prepared AI orchestration and observability. Shared validated contracts keep native and web actions consistent later.

Atomically schedule and create the durable job after checking the exact approval, destination and immutable media. Claim due jobs with a persisted lease; commit before network calls. Immediately before dispatch, lock workspace access/plan control then publication, recheck live membership/entitlement/permission/approval/cancellation and atomically record `dispatch_started`. Quota/plan/member changes and cancellation/revocation/edit commands use that same lock order; multiple publication locks use consistent ordering. Commit before HTTP; never hold a DB transaction over provider work. Write completion only with the matching lease token. Checkpoint uploads/provider identifiers and schedule follow-up status work rather than blocking on a long upload/poll loop.

Vercel cron is best effort and does not retry failures; missed/duplicate/overlapping wake-ups are normal failure cases to test. Catch up outstanding jobs with a proposed **15-minute lateness limit**: within it attempt eligible work; beyond it require an owner decision. This is a configurable product default, not a provider guarantee. [Cron behaviour](https://vercel.com/docs/cron-jobs/manage-cron-jobs)

Distinguish safe retries from uncertain create outcomes. `outcome_unknown` requires reconciliation or manual verification before a fresh create. Cancellation prevents unstarted work; in-flight requests can still succeed, so show `cancel_requested` until settled. Editing public content creates a new revision/reapproval; changing only time uses explicit rescheduling permission/audit. After dispatch starts, edits create unsent draft work and cannot replace the in-flight snapshot. Worker reads the approved snapshot, never an unrelated newest draft.

All five networks have initial product support, using the accepted manual route where direct publishing is blocked. Implement direct adapters incrementally without omitting a launch network from planning/review/history. Each account/format records technical capability (`supported`, `unsupported`, `permission_required`, `unverified`) separately from delivery route and budget gate. Show the actual route/reason. ## 11. Developer experience and release workflow

Use a pinned pnpm version and committed lockfile, strict TypeScript, ESLint/Prettier and small branches into protected `main`. Document local setup, required secret names, database reset and synthetic fixtures. Define the repository's check scripts during Phase 0; this planning workspace has no application commands to run.

CI checks formatting, lint, types, domain tests, real database/RLS tests, critical browser journeys and production build. Run provider contract fixtures without real publishing. Preview deployments use isolated test data and test credentials; they must not inherit production social grants or activate a production publisher.

Use one SQL migration history. Review grants, RLS, indexes and backwards compatibility together. Generate database types from the resulting schema and fail CI on drift. Expand schema first, deploy compatible code, migrate data when needed, then remove obsolete fields in a later release. No automatic destructive migration on every preview.

Release sequence: verify checks and backups, apply reviewed compatible migrations, deploy application, check authenticated readiness and a controlled account operation, then enable any new adapter. Roll back the application or disable the adapter if needed; database rollback requires a specific recovery procedure. Pause and reconcile uncertain external work before restarting a publisher after recovery.

## 12. Testing strategy

| Layer | High-value cases |
| --- | --- |
| Domain/unit | Exact approval coverage, canonical public-payload hash, format validation, source permission, state transitions, explicit rescheduling, missing/repeated DST times |
| Real database | Cross-workspace/indirect-ID attacks; role grants/RLS; Free fourth-network/fourth-account/same-network second-account denial; fifth-seat races/sixth-seat trusted grants; invitation expiry/acceptance without double-counting; client seat-grant denial; last-owner/non-destructive reduction; reconnect versus new identity; downgrade/revocation; atomic schedule/job writes; immutable revisions/media; stale leases |
| Provider contracts | Expired/revoked grants, rate limits, media processing, response lost after successful create, duplicate wake-ups, safe retry versus unknown outcome, cancellation during dispatch |
| Browser journeys | Capture → revise → self-approve → calendar → manual/provider confirmation; failed/conflicting autosave; reconnection; keyboard and screen-reader operation |
| Prepared AI | Exact Free allow-list admission/premium denial; family/disguised follow-up bypass rejection; finite quota races; role/source/release gates; authorised inputs only; strict task/proposal schemas; reservation release/idempotency; accept suggestion into a normal revision; test-only fake unavailable in production |
| Video analytics | Missing bins; coarse quartiles/average-only evidence; valid rewatches or values over 100% under the source definition; zero/unknown/mismatched denominators and cohorts; edited/wrong transcripts or unverified cut/offset mappings; cache invalidation; unsupported timestamp/causal claims |
| Operational | Accepted schedule with browser/phones closed; missed cron catch-up; controlled reconciliation; restore DB plus media plus encryption-key dependencies |
| Real devices | Safari/Home Screen web app on both pilot phones, upload/copy/download, text enlargement, slow connectivity and preserved work; native memory/thermal/offline tests only when funded |

Use two isolated test workspaces before any public beta. A browser test passing is insufficient evidence of database isolation or publishing reliability. Fake-provider tests must reproduce acceptance followed by response loss; absence of a returned post ID cannot be treated as proof of failure.

Live provider tests use expressly selected owned test accounts and harmless approved content during implementation. Record the permitted account/format/API version. Never turn CI into an unattended live-posting suite. Verify the restore procedure against a disposable environment and reconcile simulated external posts before resuming.

## 13. Observability and SRE-lite

Record structured request/job/attempt correlation IDs, outcome category, duration, provider and safe identifiers. Avoid tokens and private draft text in logs. Track publisher heartbeat, oldest due job, scheduling lag, uncertain results, failures/reconnections, database/storage usage and workflow completion/editing time. Separate manual confirmations from provider confirmations in every metric.

Provide a private operations page and minimal liveness/readiness checks; protect dependency details. Proposed pilot alerts: three missed minute heartbeats, eligible jobs more than two minutes late, and any uncertain publishing result. Tune thresholds against observed behaviour; the 15-minute limit controls whether late work proceeds, while an earlier alert permits intervention. Display action-needed states in Cadence; add external notification delivery only when its channel/cost is chosen.

The three initial runbooks are:

1. **Account disconnected:** pause affected jobs, explain the required reconnection, verify destination/permissions, re-evaluate overdue work and resume only eligible work.
2. **Post missing, late or outcome unknown:** inspect checkpoint/lease/provider ID; query permitted provider status or verify manually; record evidence, resolve status, then decide whether a new create is safe. Never retry an unknown create automatically.
3. **Restore after data loss:** disable dispatch; restore database, private assets and key dependencies; validate memberships/approvals/media; reconcile external results and overdue work; record achieved RPO/RTO before enabling publishing.

## 14. Milestones and step-by-step delivery

Estimates assume one experienced full-time developer, prompt access to owned accounts and no major design change. They are planning ranges; platform approvals and model/device compatibility have no guaranteed completion date. Work through six milestones, each ending in a usable or testable result.

### Phase 0 — settle scope and establish the repository

**Indicative effort: 5–7 working days.** Each item is delivered as its own numbered PR, in order.

- **0.1 — Git repository, protected base, tooling and CI:** preserve the existing docs/research bundle; add private-repository setup, local-secret exclusions, a history secret scan, and a least-permission PR check. Define dev/preview/production secret separation and prohibit preview publishing. No user data, cloud resources or app behavior is introduced in this step.
- **0.2 — Database and access foundation:** define tenant-consistent relationships, Clerk subject mapping, protected pilot/MFA policy, source grants and erasure state; implement SQL migrations, restricted roles, RLS/Storage policies and pooled actor-context controls with synthetic cross-tenant, alternate-path and policy-mode tests.
- **0.3 — Design tokens and application shell:** recover/confirm the approved visual assets and build responsive shell/tokens with synthetic sample data, visible private/shared/destination state and denial recovery. Apply the requested Apple design skills to web patterns and validate keyboard, enlarged text, contrast, light/dark and reduced-motion behavior.

**Phase 0 exit:** 0.1, 0.2 and 0.3 each have a separate PR with passing current-revision CI and verified merge evidence. Synthetic-only previews remain mandatory through step 1.8. Record five-network/account capability evidence during provider-adapter steps; account names, grants and source rights are setup inputs, not assumed. AI contracts use fixtures only; no inference subscription or model benchmark is part of this phase.

### Phase 1 — useful editorial web app

**Indicative effort: 4–6 weeks for the expanded accounts/Teams/formats/AI-preparation scope.**

- [ ] Implement separate logins, Teams membership/roles, workspace/brand/account permissions, playbooks, source capture and private immutable media.
- [ ] Implement Free/Creator/Professional/Teams entitlements, atomic connection/invitation limits, stable account identities, manual destinations and reconnect handling; use protected internal plan/additional-seat assignment rather than checkout. Teams counts owners and unexpired reserved invitations within five plus grants; acceptance converts the reservation once.
- [ ] Protect the last owner and implement explicit blocked-publication reasons/revalidation, including permission/approval/lateness tests.
- [ ] Build Today, Library/Capture, composer/autosave, revision review and self-approval with clear error/conflict states.
- [ ] Implement week/list calendar, explicit time-zone scheduling and publication history.
- [ ] Include all five networks with text/image/carousel/landscape/vertical-video preparation as genuinely supported; build destination-specific validation/preview and accepted manual handoffs. Keep YouTube out of launch.
- [ ] Build AI task/input/prompt/output contracts, permission checks, persisted run/proposal states, reservations and reusable suggestion review. Prove the pipeline with synthetic fixtures; production execution remains disabled.
- [ ] Prepare `packages/analytics/video-evidence.schema.ts`, metric definitions, time-bin/fact contracts, immutable video/transcript identity and verified timeline/provenance validation. Keep calculations independent of models/provider credentials; use authorised manual evidence and synthetic fixtures. Add missing-bin/coarse-quartile/rewatch/denominator/transcript-edit/wrong-timeline tests before interpretation.
- [ ] Implement source-use, revision, media and account boundaries from the engineering companion; test both users and indirect object access.

**Acceptance:** separate FSS logins complete the editorial loop across all five networks and permitted format representations. Plan/account/role limits survive direct API calls and concurrent requests; Free rejects a fourth network/account and a second account on a selected network, Teams permits five occupied/reserved seats and requires a trusted grant for a sixth, and Professional has no account-count ceiling. Invitation conversion/expiry, client grant denial and non-destructive capacity reduction tests pass. Saved work/approval/isolation and video-evidence contract checks pass. Exact-feature AI preparation passes fixture tests; entitled-but-deferred Free and paid tasks create no production work.

### Phase 2 — reliable authorised automatic posting

**Indicative effort: 3–6 weeks for initial verified direct adapters and format processing; reviews can extend this.**

- [ ] Build the durable job consumer, 45-second execution budget, leases/checkpoints, safe backoff, status polling and reconciliation.
- [ ] Implement one verified account/format adapter first, then verified LinkedIn/Facebook/Instagram routes; preserve accepted manual TikTok/X routes and unsupported native features. Each additional format passes its own gate.
- [ ] Add account health/reconnection, cancellation states, explicit rescheduling and an owner-controlled pause.
- [ ] Enforce effective plan/account/role changes at scheduling/dispatch; preserve immutable in-flight attempts and reconcile them on downgrade/revocation.
- [ ] Prove response-loss, overlap, stale-worker, revoked-grant, rate-limit, media-processing and daylight-saving cases.
- [ ] Add operations metrics and the three runbooks; restore media/database/key dependencies in a disposable environment.

**Acceptance:** an approved scheduled test post publishes while phones/browser are closed. Duplicate wake-ups do not trigger blind duplicate creation; uncertain outcomes are visible and recoverable; content or destination changes require fresh approval. An unsupported/paid/review-blocked route stays manual. X API fees and TikTok internal Direct Post are outside this milestone's automatic scope.

### Phase 3 — prove the internal product

**Minimum observation: four weeks of real use; allow 1–2 additional development weeks for fixes.**

- [ ] Use Cadence for the agreed brands every week; log saved time, repeated friction, posting failures and editing effort.
- [ ] Add reusable templates and light learning notes where real workflow evidence supports them.
- [ ] Add permitted metric snapshots; label missing/unavailable measurements rather than displaying zero. Compare like-for-like formats and time windows.
- [ ] Implement deterministic retention facts and accessible reporting from authorised API/manual evidence, retaining definitions, bins, source/window, denominator/cohort and permission/freshness. Offer interval-linked video/transcript inspection only for the exact published cut or a verified mapping; numeric reporting works without speech data. No AI diagnosis runs in this milestone.
- [ ] Prepare consent-aware analytics/trend inputs and task evaluation examples; do not send restricted API data to a model. Gather time-to-post and editing baselines for later AI evaluation.
- [ ] Fix recurring issues and test recovery, account revocation, deletion/export and retention settings.
- [ ] Review baseline cost, manual effort and reliability with both owners; agree which direct adapters remain worth maintaining.

**Acceptance:** four weekly content cycles complete, no unresolved data-loss/isolation issue remains, and each publishing incident has a recorded resolution. Deterministic analytics/manual evidence reports show their actual precision/coverage and reject wrong denominators/timelines; no invented timestamps or causal conclusions appear. Restore targets are measured. The owners can identify concrete value and remaining friction before advertising.

### Phase 4 — funded hosted AI and native offline AI

**Prerequisite: project revenue funds development and operating costs. Indicative effort: 4–8 weeks after a successful model/device feasibility spike; revise the estimate from measured results.**

- [ ] Revalidate the existing research, licence/distribution terms and current hosting quotes; choose a bounded hosting allowance and data policy before deploying inference.
- [ ] Blind-test one candidate and a smaller fallback on permitted FSS examples: factual fidelity, brand fit, editing effort, latency and memory. The prior model comparison is a shortlist, not a benchmark result.
- [ ] Connect a real hosted runtime to the prepared pipeline, tune task prompts and measure usage. Activate limited Free-and-above alt text and analytics only after their feature-specific evaluation, source/modalities and finite quotas pass; enable broader Creator/Professional/Teams captions/repurposing, bio/SEO-name and evidence-backed next-post/trend tasks separately.
- [ ] Evaluate `video_retention_diagnosis` against measured facts and human-reviewed explanations; separate observation, possible causes and next editing test. Reject fabricated speech, causal attribution or timestamp precision; suppress quote alignment when the transcript/published cut mapping is unverified. Replacement hooks/captions/scripts require a separate paid feature request; Free diagnostics cannot bypass that boundary.
- [ ] Launch analytics/trending features only with permitted, sufficiently covered inputs; label scope, source/date and uncertainty. AI explanations do not calculate metrics or invent a global trend feed. Profile optimisation proposes edits; auto-writing profiles needs a separately verified endpoint/grant.
- [ ] Build SwiftUI capture, local drafts and versioned sync; use the same server permission and publication contracts. Offline schedules remain unaccepted until the server acknowledges them.
- [ ] Implement and test an offline model route for each certified native device. Evaluate Apple's system model on eligible phones and an optimized downloadable Gemma candidate where needed; use on-demand model delivery rather than automatically putting multi-gigabyte weights in every installation.
- [ ] Test first download/update/interruption, licence notices, artifact integrity, free storage, long sessions, app suspension, thermal load and generation with network access disabled. Certify exact device/OS/runtime/model/task combinations.

**Acceptance:** funded web AI improves measured editing effort and explanation usefulness without granting publish authority. Free receives only its released alt-text/analytics allow-list within finite allowance; broader generation remains Creator-and-above. Every advertised native offline feature actually works on certified devices under feature-specific signed entitlements and local budgets; cloud access does not bypass premium restrictions. Define/test offline-entitlement expiry/grace before sales, rather than promising immediate revocation while disconnected. Video fidelity/precision/causality and missing-evidence tests pass. iPhone 13 support remains unverified until the local route passes; hosted fallback does not satisfy the offline requirement. An 8 GB label alone is insufficient. No universal compatibility or unlimited-free-hosting promise is made.

### Phase 5 — controlled public beta, then advertising

**Indicative effort: 2–4 weeks for web beta readiness after Phase 3; platform reviews can extend this.**

Web beta may follow Phase 3 without waiting for AI funding. Native distribution requires Phase 4's offline/device gates and Apple membership.

- [ ] Invite five–ten independent testers across tier/role fixtures; validate existing membership/account policies and workspace isolation with truthful supported-network/format descriptions.
- [ ] Complete required public-provider permissions/reviews for the five launch networks. Keep accepted manual routes for unavailable/paid capabilities; YouTube reviews belong to its later roadmap addition.
- [ ] Prove onboarding/recovery email delivery, abuse controls, export/deletion, privacy/retention documentation, backup restoration and incident ownership.
- [ ] Measure a beta workload against connection, cron-duration, storage, egress and social-rate-limit budgets. Confirm spend alerts and an agreed upgrade point.
- [ ] Before selling Teams, agree extra-seat pricing and explicit reduction/grace policy; prove that seat cancellation preserves a last owner, all content and history, with no silent member removal. Verified billing grants must pass the same capacity and audit checks as internal operations.
- [ ] For native release, run TestFlight/device coverage, model-pack compatibility and App Review preparation. Ensure offline functionality is accurately described.
- [ ] Advertise after usability, support and reliability findings are resolved. Design pricing/billing only after the commercial offer is agreed.

**Acceptance:** independent testers complete the core loop; customer A cannot access customer B through any tested object path; restore/reconnection/reconciliation drills pass; costs fit the agreed allowance; public claims match verified capabilities.

## 15. Main risks and mitigations

| Risk | Concrete mitigation |
| --- | --- |
| Five-network support mistaken for every native format being automatic | Verified account/format routes, accepted manual handoff and explicit representation/review; keep X fees and TikTok internal restriction visible |
| Provider examples or policies become stale | Pin a supported API version, reverify official documentation and actual grants before each adapter/release |
| Duplicate posts after response loss | Persist dispatch/checkpoints, distinguish unknown from safe failure, reconcile before fresh create |
| Lost drafts or stale approval | Immutable revisions/media, optimistic versions, atomic approval/scheduling and autosave recovery |
| Cross-workspace data or token exposure | Composite relationships, RLS/grants plus server permissions, private token access, redacted logs and negative tests |
| Database restore lacks media/keys or repeats external posts | Independent asset/key recovery, restore drill, paused dispatch and external reconciliation |
| Hosting quota/overage or minute-scale delay | Usage monitoring, bounded batches, catch-up policy, owner alerts and measured capacity before expansion |
| Local AI does not fit a target phone | Defer claims; actual device/runtime/task benchmarks; smaller artifact where acceptable; native release gate for certified offline support |
| AI preparation expands into unfunded inference | Build the explicitly requested contract/state/review infrastructure and fixture tests; defer model execution, hosting and evaluation until funded |
| Plan/role bypass, quota race or destructive downgrade | Server/DB current policies, transactional capacity reservation, negative/concurrency tests and preserved history/in-flight snapshots |
| AI trends/analytics mislead or misuse provider data | Deterministic metrics, permitted-input rules, dated sources/coverage, minimal-sample gates and no fabricated trend/SEO promises |
| Review workflow becomes a household bottleneck | Both pilot owners can self-approve; keep exact-revision review explicit without compulsory second-person review |
| Public data obligations exceed pilot setup | Review processor/data-policy scope, provider retention, onboarding, export/deletion and incident procedure before public onboarding |

## 16. Post-MVP roadmap

Near-term improvements follow observed use: reusable campaign/series templates, bounded recurring schedules, bulk import, additional verified formats and useful analytics. Prioritise improvements that reduce repeated work over a large social inbox or video editor.

Funded AI can expand to stronger repurposing, multilingual variants, source summaries, voice capture/transcription and image/video understanding after separate permission, quality and resource gates. Preserve user review and deterministic calculations. Provider-derived data is not a general-purpose AI training or prompt source.

Customer roles/invitations and plan enforcement belong to the initial build. Growth work adds checkout against that assignment boundary, agreed usage pricing, support tooling, additional measured capacity and later YouTube integration. Extract a persistent publisher/API only when measured workloads warrant it. Evaluate Android when requested.
