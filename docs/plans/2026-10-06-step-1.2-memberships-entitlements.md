## Scope and acceptance

Implement the server and database boundaries for member invitations, role
changes/removal, trusted plan/seat assignments, and destination activation.
Preserve private-source isolation. Every sensitive command needs a live Clerk
session, authentication within ten minutes, current database membership and the
permitted role. Missing policy, entitlement or permission denies access.

- Owners manage membership and ownership; admins manage non-owner members.
  Neither can self-promote or grant themselves paid plans or additional seats.
- Editors and publishers retain their documented content permissions, but cannot
  manage memberships or account connections. Viewers cannot mutate resources.
- Concurrent owner demotions/removals cannot leave a workspace without an owner.
  Removal blocks later authorised reads/commands without waiting for JWT refresh.
- Teams includes five active/reserved logins, counting owners. Only separately
  provisioned internal operations can grant additional capacity. Unexpired
  invitations reserve capacity; acceptance consumes that reservation once.
- Free permits three selected launch networks, three enabled destination
  identities total and one per network. Creator permits one per launch network.
  Professional and Teams have no plan-level account-count ceiling. Manual
  destinations count; reconnecting the same identity does not consume a new slot.
- Downgrades preserve identity/history/content and require a valid retained
  account selection. Reject capacity reductions below occupied/reserved seats.
  Later dispatch must read current entitlements; no publishing jobs exist yet.

Public prices, checkout and non-Teams user/workspace allowances remain undecided.
Do not infer a public solo seat policy or implement billing. Missing collaborative
seat policy on a non-Teams plan denies new invitations rather than promising
unlimited capacity. Public onboarding remains closed.

## Implementation boundaries

1. Add focused shared Zod command/response contracts and machine-readable errors.
   Identity/role fields come from verified server context, never request actors.
   Validate UUIDs, launch-network enums, optimistic versions and idempotency keys.
2. Add a restricted server database connection with transaction-local actor and
   verified claim context. Check Clerk session activity and factor freshness
   before mutation. Always reset context on commit/rollback through transaction
   scope; never use the webhook service-role key for user commands.
3. Add versioned protected plan catalog/assignments, invitation reservations,
   destination identities/selections and minimal audit/command receipt records.
   Use tenant-consistent foreign keys, private schemas, RLS and explicit grants.
   Internal plan/seat administration has a separate non-login role and audited
   reason/origin; application users cannot obtain that role.
4. Serialize membership, invitation, seat and destination admissions on one
   workspace control lock. Recheck identity, membership, policy and current
   limits after acquiring the lock. Use conditional versions and idempotency
   receipts to reject stale changes and avoid duplicate reservations.
5. Keep API routes thin; separate authorization, membership, entitlement and
   destination services. Expose no raw table-write RPC to browser roles. Add
   explicit account grants where members need less than workspace-wide access.
6. Implement invitation issue/revoke/accept without sending email. Bind a hashed,
   expiring, one-use acceptance secret to the intended verified internal user.
   Return any invitation secret only in a no-store response; never log or persist
   its plaintext. Define retry/reissue behavior if that response is lost.

Use existing tools and versions. A Postgres driver is justified by restricted-role
transactional commands; shared Zod validation is already required by the project
architecture. Avoid UI redesign in this unit; any necessary UI follows Stitch
and the two requested Apple skills.

## Data handling and verification

Admitted data: synthetic internal user/workspace IDs, roles, provider identity
references, plan/version identifiers, invitation-secret hashes, expiry and safe
audit reason codes. Do not store emails, private content, OAuth tokens, invitation
plaintext or webhook payloads in these tables or logs. Provider identity labels
are private metadata, visible only to authorised workspace/account members.

Store authoritative state in private Postgres. Pending invitations expire and
release capacity; revoked invitations cannot be accepted. Operational cleanup,
180-day minimal audits and erasure integration must follow the retention plan.
Member removal preserves content ownership and history without granting another
owner access to private captures. Recovery remains the separate future audited
source command. No browser persistence or shared caching is added.

Verification must cover:

- Role matrix, owner/admin escalation, self-grants, last-owner protection,
  forged actors, stale/disabled sessions and cross-tenant indirect IDs.
- RLS and direct REST/RPC/Storage denial of alternate mutation/read paths.
- Concurrent final-seat invitations, acceptance without double counting,
  expired/revoked invitations, duplicate requests and unsafe seat reductions.
- Concurrent Free/Creator final account slots, manual identity limits,
  idempotent reconnect and Professional multi-account admission.
- Trusted plan/seat writes versus user/owner attempts, downgrade selection,
  version conflicts and preservation of membership/content/history.
- Transaction context reset on success/failure, secret-marker log exclusion,
  formatting, lint, strict types, unit tests and production build.

Run real database and concurrency tests in CI when local Docker is unavailable.
Generate database types from the migrated test schema and keep them checked.
Record exact revision, test results and host merge in delivery evidence before
starting step 1.3. A plan, local commit or open PR is not a completed delivery unit.
